# รายงานวิเคราะห์สาเหตุอาการดับ/รีเซ็ตตัวเอง — Water Quality (env:Sensor_3)

- **วันที่:** 23 พ.ย. 2026
- **บอร์ด:** LilyGO T-Call SIM800L (V1.4) + LCD 20x4 I2C + ADS1115 + DS18B20 + GPS + Rotary encoder
- **ภาคจ่ายไฟปัจจุบัน:** 18650 ×4 (ขนาน) → TP4056 → MT3608 (5V) → บอร์ด
- **โค้ดที่ตรวจ:** ทุกไฟล์ใน `src/` และ `include/` ที่ถูกคอมไพล์ใน env:Sensor_3 (branch `feature/ota` รวมงานที่ยังไม่ commit)
- **ขอบเขต:** รายงานนี้เตรียมไว้ใช้ **กรณีเปลี่ยนไปจ่ายไฟผ่าน IP5306 แล้วอาการยังไม่หาย** จึงเน้นหาสาเหตุฝั่งซอฟต์แวร์ และบอกวิธีพิสูจน์ว่าเป็นซอฟต์แวร์จริงหรือไม่

---

## 0. สรุปสั้น

1. **ยังสรุปจากการอ่านโค้ดอย่างเดียวไม่ได้ ว่าเป็นซอฟต์แวร์หรือฮาร์ดแวร์** ต้องดู *reset reason* ของ ESP32 ก่อน (หัวข้อ 2) วิธีนี้แยกได้ชัดเจนว่าเป็นไฟตก โปรแกรม crash หรือโปรแกรมค้าง
2. ฝั่งซอฟต์แวร์ **ไม่มีจุดไหนที่ทำให้เครื่องรีเซ็ตเองระหว่างที่แค่เปิดหน้าวัดค่าไว้เฉยๆ อย่างชัดเจน** จุดเสี่ยงที่เจอมักเกิดตอนทำบางอย่าง เช่นบันทึกค่า ส่งข้อมูล หรือเช็ค OTA
3. จุดที่ซอฟต์แวร์มีส่วนทำให้ไฟตกจริง คือ **SIM800L ถูกเปิดและหาเครือข่ายตลอดเวลา แม้อยู่ในโหมด WiFi** และ**สั่ง restart โมเด็มซ้ำทุกประมาณ 11 นาทีเมื่อต่อเครือข่ายไม่ติด** ทุกครั้งจะเกิดกระแสพีคประมาณ 2A
4. จุดเสี่ยงที่จะทำให้ **crash จริง** (ESP_RST_PANIC) คือ **stack ของ Input task (2048 B) และ Sound task (1024 B) อาจไม่พอ** โดยเฉพาะตอนเขียน NVS
5. **แก้ข้อมูลที่ผมให้ไว้ก่อนหน้า:** โปรเจกต์ไม่ได้ใช้ Arduino core 2.0.17 แต่ build จริงใช้ **pioarduino platform 55.3.39 / Arduino core 3.3.9 / ESP-IDF 5.5.4** และ `platformio.ini` ไม่ได้ล็อกเวอร์ชันไว้ (หัวข้อ 3.6)
6. ข่าวดี: firmware นี้ **เปิด core dump ลง flash ไว้แล้ว** และ partition table มีพื้นที่ `coredump` อยู่แล้ว ถ้าเครื่อง crash จะดึงข้อมูลได้ว่า crash ที่ task ไหน บรรทัดไหน (หัวข้อ 5.4)

## 2. วิธีแยกสาเหตุ: อ่าน reset reason ก่อนทำอย่างอื่น

ค่าจาก `esp_reset_reason()`:

| ค่า | ชื่อ | ความหมาย | ทิศทาง |
|---|---|---|---|
| 1 | `ESP_RST_POWERON` | ไฟดับไปทั้งหมด | ฮาร์ดแวร์: ไฟขาด, ขั้วหลวม, IP5306 ตัดไฟ |
| 9 | `ESP_RST_BROWNOUT` | แรงดันตกชั่วขณะ | ฮาร์ดแวร์/ไฟ: พีคจาก SIM800L, ภาคจ่ายอ่อน |
| 4 | `ESP_RST_PANIC` | โปรแกรม crash (exception, stack overflow, assert) | **ซอฟต์แวร์** ไปดู core dump |
| 5 | `ESP_RST_INT_WDT` | interrupt/critical section ค้างเกิน 300 ms | **ซอฟต์แวร์** (หรือ ISR/driver) |
| 6 | `ESP_RST_TASK_WDT` | task ค้างจน idle ไม่ได้ทำงาน | **ซอฟต์แวร์** |
| 7 | `ESP_RST_WDT` | watchdog อื่น | ซอฟต์แวร์/ฮาร์ดแวร์ |
| 3 | `ESP_RST_SW` | มีโค้ดสั่ง `ESP.restart()` | ซอฟต์แวร์ตั้งใจรีเซ็ต: OTA สำเร็จ หรือ factory reset (ข้อ S-9) |

**สังเกตด้วยตาก็ช่วยได้:**
- จอ LCD ดับมืดสนิทแล้วค่อยติดใหม่ มักเป็นเรื่องไฟ
- จอกระพริบแวบเดียวแล้วขึ้นหน้า "System Ready" ทันที อาจเป็นซอฟต์แวร์ crash หรือ brownout ก็ได้

**การทดลองที่แยกได้เร็วที่สุด:** จ่ายไฟบอร์ดด้วย adapter 5V 2A ที่ดี ไม่ผ่านแบต TP4056 หรือ MT3608 แล้วเปิดทิ้งไว้นานกว่าช่วงที่เคยดับ 2–3 เท่า
- ถ้า**ไม่ดับ** แปลว่าปัญหาอยู่ที่ภาคจ่ายไฟ
- ถ้า**ยังดับ** ให้ดู reset reason แล้วไล่ตามหัวข้อ 3

## 3. ผลการตรวจโค้ด (เรียงตามโอกาสที่ทำให้รีเซ็ต)

ระดับ: 🔴 ทำให้รีเซ็ตได้จริง · 🟠 มีส่วนทำให้รีเซ็ต หรือเกิดในบางเงื่อนไข · 🟡 ไม่ทำให้รีเซ็ตโดยตรง แต่ทำให้หาสาเหตุยากหรือมีผลข้างเคียง

### 3.1 กลุ่มที่ทำให้เกิดกระแสพีค (ซอฟต์แวร์ทำให้ไฟตกหนักขึ้น)

#### 🔴 P-1 — SIM800L เปิดอยู่ตลอด แม้ใช้โหมด WiFi
- **ที่:** [SimTask.cpp:78-92](../src/SimTask.cpp#L78-L92) (ตอนบูต), [SimTask.cpp:103](../src/SimTask.cpp#L103) (โหมด WiFi)
- **สิ่งที่เกิด:** ตอนบูต ไม่ว่าจะตั้งโหมดไหน โค้ดจะสั่ง `MODEM_POWER_ON = HIGH` และ `modem.restart()` เสมอ พออยู่ในโหมด WiFi ก็แค่ `vTaskDelay(1000)` แล้วข้ามไป ไม่มีจุดไหนปิดไฟโมเด็ม
- **ผล:** ถ้ามีซิมเสียบอยู่ SIM800L จะลงทะเบียนเครือข่ายและส่งสัญญาณเป็นระยะ ทำให้เกิดพีค ~2A แม้ผู้ใช้เลือก WiFi ถ้าสัญญาณอ่อน พีคจะถี่ขึ้น
- **แนวทางแก้:** โหมด WiFi ให้สั่ง `MODEM_POWER_ON = LOW` และเปิดกลับพร้อม `modem.restart()` เมื่อเปลี่ยนเป็นโหมด SIM

#### 🔴 P-2 — Auto-recovery สั่งรีสตาร์ทโมเด็มซ้ำทุก ~11 นาที เมื่อต่อเครือข่ายไม่ติด
- **ที่:** [SimTask.cpp:132-145](../src/SimTask.cpp#L132-L145)
- **สิ่งที่เกิด:** แต่ละรอบเรียก `waitForNetwork(60000)` ถ้าไม่สำเร็จจะเพิ่ม `failCount` ได้ประมาณ 1 ครั้งต่อนาที พอเกิน 10 จะดึง `MODEM_RST` ลง LOW แล้วตามด้วย `modem.restart()` ช่วงที่โมเด็มบูตและหาเครือข่ายใหม่คือช่วงที่กินกระแสสูงที่สุด
- **อาการที่จะเห็น:** ถ้ารีเซ็ตเกิดเป็นจังหวะประมาณ 10–12 นาที (หรือหลังเปิดเครื่องได้ราว 11 นาที) ในโหมด SIM ข้อนี้เป็นผู้ต้องสงสัยหลัก
- **แนวทางแก้:** ใช้ backoff เพิ่มระยะห่างขึ้นเรื่อยๆ (เช่น 1 → 5 → 15 นาที) จำกัดจำนวนครั้งที่ restart และถ้าไม่ได้ใช้โหมด SIM ให้ปิดไฟโมเด็มไปเลย

#### 🟠 P-3 — WiFi เรียก `WiFi.begin()` ใหม่ทุก 5 วินาทีเมื่อต่อไม่ติด
- **ที่:** [WifiTask.cpp:106-113](../src/WifiTask.cpp#L106-L113)
- **สถานะ:** ลด TX power เหลือ 13 dBm แล้วในรอบนี้ (ยังไม่ commit)
- **ที่เหลืออยู่:** การสแกนและเชื่อมต่อทุก 5 วินาที ทำให้มีพีค RF ซ้ำๆ แนะนำให้ปรับเป็น 15–30 วินาที หรือใช้ `WiFi.setAutoReconnect(true)` แล้วไม่ต้องเรียก `begin()` ซ้ำ

#### 🟡 P-4 — โหลดอื่นที่ลดได้ด้วยซอฟต์แวร์
- **CPU 240 MHz:** ถ้าลดเป็น 80–160 MHz ด้วย `setCpuFrequencyMhz()` จะลดกระแสเฉลี่ยได้ราว 20–30 mA (เป็นค่าประมาณ) WiFi ยังทำงานที่ ≥80 MHz ได้
- **LCD วาดทุก 25 ms** ([ScreenManager.h:10](../include/ScreenManager.h#L10)): ทั้ง CPU และ bus I2C ทำงานแทบตลอด จอ 20x4 ไม่จำเป็นต้องวาดถี่ขนาดนี้ 100–200 ms ก็พอ
- **Buzzer ระดับ 3** ([Alarmtask.cpp:76](../src/Alarmtask.cpp#L76)) ดังทุก 300 ms ต่อเนื่อง ถ้าต่อ buzzer ตรงเข้า GPIO2 จะดึงกระแสจากขาโดยตรง

### 3.2 กลุ่มที่ทำให้ crash จริง (ESP_RST_PANIC)

#### 🔴 S-1 — Stack ของ Input task (2048 B) เสี่ยงล้นตอนเขียน NVS
- **ที่:** [main.cpp:48](../src/main.cpp#L48) และ handler ที่เรียก `NVSManager::save*/load/reset` ใน Input task ได้แก่ [StateMachine_3CH.cpp:274](../src/StateMachine_3CH.cpp#L274), [:350](../src/StateMachine_3CH.cpp#L350), [:359](../src/StateMachine_3CH.cpp#L359), [:402](../src/StateMachine_3CH.cpp#L402), [:410](../src/StateMachine_3CH.cpp#L410), [:483](../src/StateMachine_3CH.cpp#L483), [:560](../src/StateMachine_3CH.cpp#L560), [:564](../src/StateMachine_3CH.cpp#L564), [:650](../src/StateMachine_3CH.cpp#L650)
- **กลไก:** ใน ESP-IDF 5 ฟังก์ชัน `Preferences` → `nvs_set_*` / `nvs_commit` ทำงานบน stack ของ task ที่เรียก และใช้ stack มากพอสมควร เมื่อรวมกับ `handleEvent` และ `SensorData` ที่อยู่บน stack ด้วย พื้นที่ 2048 B มีโอกาสเกินขอบ ระบบ canary จะจับได้และขึ้น `Stack canary watchpoint triggered (Input)` แล้วรีเซ็ต
- **อาการที่จะเห็น:** รีเซ็ต**ทันทีหลังกดบันทึก** threshold, temp offset, calib, เปลี่ยนโหมดเครือข่าย, mute หรือ Device ID
- **แนวทางแก้:** เพิ่มเป็น 4096 แล้ววัด high-water mark (หัวข้อ 5.3)

#### 🟠 S-2 — Stack ของ Sound task (1024 B) น้อยเกินไป
- **ที่:** [main.cpp:28](../src/main.cpp#L28)
- **กลไก:** ใน Arduino 3.x `tone()` ส่งข้อความเข้า queue ของ `toneTask` และเรียก `vTaskDelay` ซึ่งต้องเก็บ context ของ task ไว้บน stack พื้นที่ 1024 B แทบไม่เหลือที่เผื่อ ถ้าเปิด log หรือเปลี่ยน core ในอนาคตก็ล้นได้ทันที
- **แนวทางแก้:** เพิ่มเป็น 2048 แล้ววัด high-water mark

#### 🟠 S-3 — String ของ OTA ถูกเขียนและอ่านจากคนละ core โดยไม่มีตัวป้องกัน
- **ที่:** เขียนใน [WifiTask.cpp:193-195](../src/WifiTask.cpp#L193-L195) (core 0) อ่านใน [ScreenManager_3CH.cpp:541](../src/ScreenManager_3CH.cpp#L541) (core 1) และใน `requestStartOta(otaDownloadUrl)` (Input task)
- **กลไก:** การกำหนดค่าให้ `String` ทำให้ต้องจองหน่วยความจำใหม่ (realloc) ถ้าอีก core กำลังอ่าน pointer เดิมอยู่ จะอ่านหน่วยความจำที่ถูกคืนไปแล้ว ผลคือ crash หรือ heap เสียหาย
- **โอกาสเกิด:** ต่ำ เพราะโดยปกติ Screen task จะวาดหน้า OTA_RESULT หลังจากเขียนค่าเสร็จแล้ว แต่ถ้าผู้ใช้กดย้อนกลับแล้วกดเช็คซ้ำเร็วๆ ก็เกิดได้ และ**จะเกิดเฉพาะตอนใช้เมนู Firmware Update**
- **แนวทางแก้:** เก็บเป็น `char[]` ขนาดตายตัว และใช้ mutex/spinlock ครอบตอนคัดลอก หรือส่งผลลัพธ์ผ่าน queue

### 3.3 กลุ่มที่ทำให้ค้าง หรือทำให้ watchdog ทำงาน

#### 🟠 S-4 — `disableCore0WDT()` ปิด watchdog ของ core 0 ไว้ ถ้าโปรแกรมค้างจะไม่มีอะไรเตือน
- **ที่:** [SimTask.cpp:75](../src/SimTask.cpp#L75)
- **กลไก:** Task WDT เฝ้าแค่ IDLE ของ CPU0 (ดู sdkconfig) พอถูกปิด ถ้า task ไหนบน core 0 ค้างแบบวนลูปไม่ปล่อย CPU เครื่องจะ**ค้างเงียบ** แทนที่จะรีเซ็ตพร้อมบอกสาเหตุ
- **สาเหตุที่น่าจะทำให้ต้องปิด:** ดู S-5
- **แนวทาง:** ตอนหาสาเหตุ ให้แก้ S-5 แล้ว**เปิด WDT กลับ** ถ้ามี task ค้างจะได้ `ESP_RST_TASK_WDT` พร้อม backtrace

#### 🟠 S-5 — TinyGSM รอข้อมูลแบบ busy-wait (`TINY_GSM_YIELD_MS = 0`)
- **ที่:** `.pio/libdeps/Sensor_3/TinyGSM/src/TinyGsmCommon.h:32` (ค่าเริ่มต้นของ library) และ [SimTask.cpp:1](../src/SimTask.cpp#L1) ที่ไม่ได้กำหนดค่านี้ไว้
- **กลไก:** `waitResponse()` วนรอ UART ด้วย `delay(0)` ซึ่งไม่ยอมปล่อย CPU ให้ task ที่ priority ต่ำกว่า SIM task (prio 2) จึงกิน core 0 ได้นานหลายวินาที ทำให้ IDLE0 และ GPS task (prio 1) ไม่ได้ทำงาน **นี่น่าจะเป็นเหตุผลที่ต้องใส่ `disableCore0WDT()`**
- **ผล:** GPS อาจได้ข้อมูลไม่ทันเพราะ buffer UART ล้น และไม่ทำให้รีเซ็ตเพราะ WDT ถูกปิด แต่เป็นจุดอ่อนที่ซ่อนอยู่
- **แนวทางแก้:** ใส่ `#define TINY_GSM_YIELD_MS 2` ไว้ก่อน `#include <TinyGsmClient.h>`

#### 🟡 S-6 — Adafruit ADS1X15 รอผลการแปลงแบบ busy-wait
- **ที่:** `.pio/libdeps/Sensor_3/Adafruit ADS1X15/Adafruit_ADS1X15.cpp:126` (`while (!conversionComplete());`) เรียกจาก [SensorTask.cpp:15](../src/SensorTask.cpp#L15)
- **กลไก:** ที่ 128 SPS แต่ละครั้งใช้ประมาณ 8 ms และ loop หนึ่งรอบอ่าน 30 ครั้ง ระหว่างรอ แต่ละรอบเป็นการอ่าน I2C ซึ่ง task จะหลับรอ interrupt จึงยังปล่อย CPU ให้ task อื่นบ้าง **ไม่น่าทำให้ค้าง** แต่ทำให้ Sensor task (prio 4) ใช้ bus I2C หนัก
- **ข้อควรระวัง:** ถ้า I2C มีสัญญาณรบกวนจนโมดูลไม่ตอบ จะติดลูปนี้ได้ ปัจจุบันยังไม่มี timeout

### 3.4 กลุ่ม I2C และ LCD (ไม่ทำให้รีเซ็ตโดยตรง แต่ทำให้ดูเหมือนเครื่องค้างหรือจอเพี้ยน)

#### 🟡 S-7 — LCD และ ADS1115 ใช้ bus I2C ร่วมกัน (อีกหน่อยจะมี IP5306 มาใช้ร่วมด้วย)
- **ที่:** [main.cpp:96](../src/main.cpp#L96), [ScreenManager_3CH.cpp:23-65](../src/ScreenManager_3CH.cpp#L23-L65), [SensorTask.cpp:80](../src/SensorTask.cpp#L80)
- **สถานะ:** Wire ใน core 3.x มี lock ต่อหนึ่ง transaction อยู่แล้ว ข้อมูลจึงไม่ปนกัน แต่ LCD วาดทุก 25 ms ซึ่งต้องส่ง transaction หลายร้อยครั้งต่อหนึ่งหน้า ทำให้ bus เกือบเต็มตลอดเวลา
- **ถ้าสาย I2C ยาว หรือมีสัญญาณรบกวนจากโมเด็มหรือหัววัด** จอจะเพี้ยน หรือ ADS จะขึ้น `ERR` ซึ่งไม่ใช่การรีเซ็ต
- **ข้อสังเกต:** ถ้าเอาแบตต่อเข้า IP5306 ซึ่งอยู่บน bus เดียวกันที่ 0x75 คำสั่ง keep-on ส่งแค่ครั้งเดียวตอนบูต ไม่กระทบ bus

### 3.6 กลุ่มสภาพแวดล้อมของ build และการตั้งค่า

#### 🟠 B-1 — `platformio.ini` ไม่ได้ล็อกเวอร์ชัน platform
- **ที่:** [platformio.ini](../platformio.ini) ใช้ `platform = espressif32` เฉยๆ
- **ข้อเท็จจริง:** เครื่องนี้ build ด้วย pioarduino 55.3.39 / core 3.3.9 แต่ถ้า build จากเครื่องอื่นอาจได้ platform ทางการ 6.x / core 2.0.17 ซึ่งพฤติกรรมของ LEDC/tone, Wire, WDT และขนาด stack ที่ใช้ต่างกัน
- **ความเสี่ยง:** firmware ที่อยู่ในเครื่องตอนนี้อาจ build ด้วย core คนละตัวกับที่ทดสอบไว้ หรือ platform อาจอัปเดตเองแล้วเปลี่ยนพฤติกรรมโดยไม่รู้ตัว
- **แนวทางแก้:** ล็อกเวอร์ชันให้ชัด เช่นใช้ URL ของ pioarduino พร้อมระบุเวอร์ชัน หรือ `espressif32@6.x.y`

#### 🟡 B-2 — ไม่มี `Serial.begin()`
- **ที่:** [main.cpp:94](../src/main.cpp#L94) (`setup()`)

### 3.7 กลุ่มฮาร์ดแวร์ที่ซอฟต์แวร์เกี่ยวข้อง

#### 🟠 H-1 — GPIO12 (RGB_G) เป็น strapping pin
- **ที่:** [Config.h](../src/Config.h) `RGB_G 12`
- **กลไก:** ถ้าวงจร LED ทำให้ GPIO12 ถูกดึงเป็น HIGH ตอนจ่ายไฟ เช่น LED แบบ common-anode ที่มีตัวต้านทาน pull-up ESP32 จะตั้งแรงดัน flash เป็น 1.8V แล้วบูตไม่ขึ้น หรือรีเซ็ตวนตอนเปิดเครื่อง
- **อาการ:** เกิดตอนเปิดเครื่องหรือหลังรีเซ็ต ไม่ได้เกิดระหว่างใช้งาน แต่ถ้ารีเซ็ตด้วยสาเหตุอื่นแล้ว**บูตกลับไม่ขึ้น** ให้สงสัยข้อนี้
- **ขาอื่น:** GPIO2 (buzzer) และ GPIO15 (RGB_B) ก็เป็น strapping pin เหมือนกัน แต่มีผลน้อยกว่า

#### 🟠 H-2 — ปุ่ม encoder โดนความชื้น จนเกิด SUPER_LONG_PRESS เอง
- **ที่:** [Rotary.cpp:85](../src/Rotary.cpp#L85), [StateMachine_3CH.cpp:357-362](../src/StateMachine_3CH.cpp#L357-L362)
- **กลไก:** ถ้าปุ่มค้าง LOW นานเกิน 10 วินาที เพราะน้ำหรือความชื้นเข้า ขณะอยู่หน้า System Info เครื่องจะ **factory reset แล้วสั่ง `ESP.restart()`** ซึ่งจะเห็นเป็น reset reason = 3 (SW)
- **โอกาสเกิด:** ต่ำ แต่เครื่องนี้ใช้งานใกล้น้ำ

## 5. แผนเก็บหลักฐาน (firmware สำหรับหาสาเหตุ)

ทั้งหมดนี้เป็นการ**เพิ่ม**โค้ดเพื่อเก็บข้อมูล ไม่ได้เปลี่ยนการทำงานหลัก แนะนำให้ทำก่อนแก้ข้อ P/S ใดๆ จะได้รู้ว่าแก้ถูกจุด

### 5.1 Reset reason + ตัวนับใน NVS (ดูได้โดยไม่ต้องต่อคอม)
```cpp
#include <esp_system.h>
void setup() {
    Serial.begin(115200);
    esp_reset_reason_t r = esp_reset_reason();
    Serial.printf("[BOOT] reset reason=%d\n", r);
    // บันทึกลง NVS: lastReason + ตัวนับแยกตามประเภท (POWERON/BROWNOUT/PANIC/WDT/SW)
    // แล้วแสดงในหน้า System Info เช่น "Rst:9 B:3 P:0 W:0"
    ...
}
```

### 5.2 Breadcrumb ใน RTC memory (ดูว่าก่อนรีเซ็ตเครื่องกำลังทำอะไรอยู่)
```cpp
RTC_NOINIT_ATTR uint32_t bc_magic, bc_uptimeS, bc_state, bc_minHeap;
// Task หนึ่งอัปเดตทุก 1 วินาที: uptime, AppState ปัจจุบัน, ESP.getMinFreeHeap()
// ตอนบูต ถ้า bc_magic ถูกต้อง ให้พิมพ์ค่าจากรอบก่อนออกมา
```
ค่าใน RTC memory จะอยู่รอดเมื่อรีเซ็ตด้วย SW, PANIC หรือ WDT แต่จะหายเมื่อไฟดับทั้งหมด (POWERON) ส่วนกรณี brownout ส่วนใหญ่ค่ายังอยู่ แต่ไม่รับประกัน

### 5.3 Health log ทุก 30–60 วินาที
- `ESP.getFreeHeap()` และ `ESP.getMinFreeHeap()` ใช้ดูว่ามี memory leak หรือไม่ ถ้าค่า min ลดลงเรื่อยๆ แปลว่ารั่ว
- `uxTaskGetStackHighWaterMark(handle)` ของทุก task ต้องเก็บ `TaskHandle_t` ไว้ตอน `xTaskCreatePinnedToCore` ซึ่งตอนนี้ส่ง `nullptr` อยู่ ถ้าค่าที่เหลือ **< 256 B** ถือว่าอันตราย

### 5.4 อ่าน core dump หลัง crash
firmware นี้เปิด `CONFIG_ESP_COREDUMP_ENABLE_TO_FLASH` และมี partition `coredump` อยู่แล้ว
- **ในโค้ด:** ตอนบูต เรียก `esp_core_dump_image_check()` และ `esp_core_dump_get_summary()` จาก `esp_core_dump.h` เพื่อพิมพ์ชื่อ task ที่ crash, ค่า PC และ backtrace
- **จากคอม:** อ่าน flash ที่ `0x3F0000` ขนาด `0x10000` แล้วใช้ `esp-coredump` ร่วมกับไฟล์ `.pio/build/Sensor_3/firmware.elf` วิธีนี้บอกได้ถึงระดับไฟล์และบรรทัด
- **สำคัญ:** ต้องเก็บไฟล์ `firmware.elf` ของเวอร์ชันที่แฟลชไว้ด้วย ถ้า build ใหม่ ที่อยู่ในไฟล์จะไม่ตรงกับ core dump

### 5.5 เปิด WDT ของ core 0 กลับ (หลังแก้ S-5)
จะได้รู้ว่ามี task ค้างจริงหรือไม่ แทนที่เครื่องจะค้างเงียบ

## 8. คำถามที่อยากให้คุณตอบ (อาจมีจุดที่ผมยังไม่รู้)

1. **reset reason ที่เห็นคือค่าอะไร** และใน Serial Monitor มีข้อความ `Guru Meditation`, `Backtrace` หรือ `Brownout detector was triggered` ก่อนรีเซ็ตไหม
2. **ตอนเกิดอาการ จอ LCD ดับมืดสนิท หรือแค่กลับไปหน้า "System Ready"**
3. **ใช้ไปนานเท่าไรถึงดับ** เท่ากันทุกครั้ง (เช่น ~11 นาที หรือ ~30 วินาที) หรือสุ่ม และดับตอนแบตเหลือประมาณกี่โวลต์
4. **ตอนเกิดอาการใช้โหมดไหน (SIM/WiFi) มีซิมเสียบอยู่ไหม** และสัญญาณ CSQ ประมาณเท่าไร
5. **ตอนดับกำลังทำอะไรอยู่** เปิดหน้าวัดค่าทิ้งไว้ กำลังส่งข้อมูล calibrate บันทึกค่า หรือ buzzer กำลังเตือน
6. **ถ้าจ่ายไฟจาก USB หรือ adapter ล้วนๆ อาการยังเกิดไหม** (การทดลอง T-1)
7. **ADS1115, GPS, LCD และบอร์ดเซ็นเซอร์ pH/EC/DO รับไฟจากขาไหน** 3.3V ของบอร์ด หรือ 5V และ LCD เปิด backlight ตลอดไหม
8. **ตอนดับ หัววัดจุ่มอยู่ในน้ำไหม** หัววัดทั้ง 3 ตัวแช่อยู่ในน้ำเดียวกันหรือไม่
9. **อาการเริ่มเกิดตั้งแต่ firmware เวอร์ชันไหน** มีมาตั้งแต่ก่อนทำ OTA หรือก่อนเปลี่ยนเป็น pioarduino/core 3.x ไหม ถ้ามี firmware เก่าที่ไม่มีอาการ จะไล่หาด้วย `git bisect` ได้
10. **firmware ที่อยู่ในเครื่องตอนนี้ build จากเครื่องไหน** เครื่องนี้หรือเครื่องอื่น และยังมีไฟล์ `firmware.elf` ของเวอร์ชันนั้นอยู่ไหม
11. **LED RGB ต่อแบบไหน** common-anode หรือ common-cathode มีตัวต้านทาน pull-up ที่ GPIO12 ไหม
12. **สาย I2C ไป LCD ยาวประมาณเท่าไร** และกล่องมีโอกาสโดนน้ำหรือความชื้นที่ encoder ไหม
13. ตอนเปลี่ยนไปใช้ IP5306 **ใส่โค้ด `setPowerBoostKeepOn(true)` ด้วยหรือยัง** และต่อแบตเข้าช่องไหนของบอร์ด
